Many standard algorithm design techniques like incremental construction or divide and conquer, try to build the solution of a large problem by combining together solutions of smaller sub-problems embedded within the larger problem. This exact same phenomenon happens in optimization as well. It's often possible to build the optimal solution of an optimization problem by carefully combining together optimal solutions of smaller sub-problems embedded within the original larger problem. This is probably best exemplified by the technique of dynamic programming, the subject of our present video. I'd like to make C cents and change using a minimum number of coins that come from a set of different denominations that I'm given. The US coin system might have one cent coins, five cent coins, 10 cent, 25 cent. For the US coin system, we know that the greedy algorithm actually works, actually gives you the minimum possible number of coins. The greedy algorithm here is just keep using the largest denomination coin that you possibly can until you've built up to C cents worth of change. For some other coin systems though, the greedy algorithm may not actually give you an optimal solution, so we need to look for alternative approaches. Remember, also, when we talked about greedy algorithms, we can have advocated this framework of thinking about how to build up a solution using sequential decisions. Basically, starting with the large problem that you're trying to solve, you just need to figure out what's the first decision in building up a solution? 

What's the first element that I add to my solution? Once you've made that first decision, you're left with a smaller residual leftover problem that conveniently has the same form as the original problem, it's only smaller. This is good news if we want to think about building big optimal solutions out of optimal solutions of smaller sub-problems or thinking recursively about constructing solutions. This is sometimes called the optimal substructure property. A problem has this property if basically the optimal way to complete a partial solution involves solving a leftover residual problem of the same form as the original, just smaller. Basically embedded within the larger problem are smaller sub-problems of the same form. After you make your first decision, you're left with a smaller sub-problem that looks the same as the original, it's just a smaller problem. 

If this property holds, that really does open the door to a wide range of different solution techniques like greedy algorithms, or as we'll see in a second, dynamic programming. Remember that with greedy algorithms, we were able to make each decision very quickly by applying some simple greedy choice rule to figure out what the first decision should be. Then we don't look back. We just keep making decisions according to that greedy choice rule. If we're looking at an exhaustive search, maybe we don't have an effective way of knowing what's the appropriate first decision to make, so you try all of them. Then after each one of those, you recursively try all possible second decisions, and you end up with this massive tree that exhaustively enumerates every possible solution. The third approach, and this is what we're going to focus on here is using dynamic programming. 

Here, we're going to basically look at every possible sub-problem that we could generate during this process, and we're going to solve them typically in a bottom-up fashion. We start with the smallest sub-problems and we solve them and we write the answers down in the table, building our way up to the largest sub-problem, which is the original problem that we wanted to solve in the first place. The benefit of doing this is that now it's easy to solve that big problem because if you look at all the possible decisions that you could make for that first decision, you have already solved the smaller sub-problems that you'll land on as a result of those potential decisions, making it easy to choose which of those decisions is the right one. We can therefore write a recursive characterization of the optimal solution for any of our sub-problem. If we define M(x) as the minimum number of coins needed to make change for x cents, then we can write a recursive expression for M(x) based on this picture. M(x) is going to be, well, one coin for whatever initial decision we make plus the minimum of whatever sub-problem we could land on after that first decision is made. We want to choose whichever of 1, 5, 10, or 25 lands on a sub-problem whose remaining solution is as small as possible. 

This is basically what a dynamic programming algorithm looks like. We have to basically define what our sub-problems are, and then we solve those sub-problems from the bottom-up, solving for M(1), M(2), M(3), all the way up to finally computing M(C), our original larger problem. All the while, we're just using this formula to compute the solution of each sub-problem as we go, and we're writing their answers down in a table. The benefit of doing that is that whenever you solve a sub-problem, you already have solved the smaller sub-problems upon which its solution depends. Here we can solve each sub-problem in just constant time, and our total running time is going to be on the order of C because we have C total sub-problems. So relatively straightforward to actually implement and analyze the running time of these algorithms. If we look at the structure and the details a little bit more closely, here are the main steps of designing a dynamic programming algorithm. 

Step 1, you should define what your sub-problems are. This is a very important step. I see a lot of students not clearly defining their sub-problems with enough clarity to make sure that the rest of the algorithm makes sense. Do take the time to very clearly and precisely define what your sub-problems are. The next step is really the crucial step. You need to write a recursive characterization of how to solve each sub-problem in terms of smaller sub-problems, sub-problems you already will have solved if you're solving them sequentially from the smallest up to the largest. Then you just simply solve all the sub-problems. 

You compute M(1) through M(C) in a bottom-up fashion. The answer is the very last problem that you've solved, M(C). You have to write the answers down in a table so that as you're solving each problem, you can just look up the answers of the smaller sub-problems on which it depends. How much space would we need for this? Well, Usually the answer would be order C space because we have to write down the answers of all the sub-problems that we're solving along the way. If you look at this specific example though, we only have to go back to x-25. Technically, we only need to keep track of the last 25 sub-problems so we could keep a rolling window of only 25 sub-problems in our past as we're solving the sub-problems as we go. 

We would technically only need constant space for this specific application. But it's very problem-specific how much space you need to keep around. If you can throw out some older state because it's less relevant, sometimes that can be beneficial for saving space. This is a recursive characterization of how to solve a problem. As with everything recursive, don't forget that you'll also need some base cases. When you get down to M(1) or M(0), some of those might be appropriate base cases to consider. There are two common ways to think about the operation of a dynamic programming algorithm. 

Probably the most standard and the most traditional is a bottom-up way of thinking about things where you take this recursive formula for computing each sub-problem solution and you just wrap it with a for loop, and you calculate sub-problem solutions from the smallest sub-problem up to the largest sub-problem. This makes implementation very easy. It also makes analysis very easy because it's very clear that we're solving C sub-problems and each sub-problem takes you constant time to solve, so the running time is order C. We could, as an alternative, though, think about a more top down recursive approach because we do have a recursive characterization for how to solve every sub-problem. We could translate that directly into a recursive function and then just call that function to compute M(C). Start with the big problem that we want to solve, and that will dispatch recursive calls to smaller sub-problems that will then further invoke even smaller sub-problems and whatnot. The trouble is if you're not careful and you just directly translate your function into a recursive implementation like this, you'll end up with an exponential running time because the tree of recursive sub-problems is going to blow up exponentially on you. 

To see how this works, let's maybe look at a slightly similar problem with pretty much the same structure. Let's look at calculating Fibonacci numbers. Remember that the nth Fibonacci number is the sum of the previous two Fibonacci numbers. You can also use dynamic programming to easily calculate the nth Fibonacci number, you just loop from one up to N, and each Fibonacci number that you compute is just the sum of the two Fibonacci numbers, you just computed before it. Almost the same type of formulation, you could also consider a recursive implementation where you ask to compute the Nth Fibonacci number, and then that calls a recursive function that will go off and compute Fib(x-1) and x-2. The trouble is if you look at the tree of recursive sub-problems that you generate by invoking the top level call, it actually does blow up exponentially. If I want to compute the seventh Fibonacci number, that's going to make a call to compute the sixth and the fifth, and computing the sixth is going to make a call to compute the fifth and the fourth and you're already solving now for the fifth Fibonacci number twice. 

The trouble that happens is you end up with, basically, repeating a lot of work. You're going to end up with the same recursive call to the same sub-problem over and over again in this tree of recursive sub-problems that gets generated. We definitely don't want to do that. That's going to give us an exponential blow up in the amount of work that we're doing. What we typically do instead is we add an extra line or two of code to our top-down recursive implementation so that once we've solved a sub-problem, we store its solution in a table. We make a memo of its solution value. This technique is sometimes called memorization. 

We basically write down the answers when we see them so that we don't have to waste work by recomputing the same sub-problem solution ever again. If you now look at what happens with this recursive tree of sub-problems, it gets pruned by memorization. Because for example, if you're computing the fifth Fibonacci number and that goes off and tries to make a call to compute the third Fibonacci number, well, you've already computed that on this other branch of calculation and written its value down in a table. You don't actually have to recursively compute that with a tree of sub-problems, you can just return the value that comes directly out of the table. This is absolutely crucial that we add memoization if we're going to use a top-down implementation. With memoization, you basically will get the same running time with a top down implementation that you would have had with a bottom-up implementation because you're basically still solving every single sub-problem once. It's just happening in a different order perhaps than in a less obvious order than things would have been in if you just looped over things and computed them in a bottom-up fashion.
