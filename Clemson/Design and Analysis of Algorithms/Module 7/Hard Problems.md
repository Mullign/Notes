If you take a class in algorithms, you might come away with the mistaken impression that every problem out there has an efficient algorithm waiting to solve it. This is mostly because we focus our attention in classes like this on problems that we actually know how to solve efficiently. Unfortunately, reality is a bit different from that. In the real world, probably most problems are actually hard or even provably hard, and we do need to have effective algorithmic strategies in hand for approaching these types of problems. We'll actually spend a good bit of time in this module and beyond talking about effective heuristics for addressing hard problems, maybe coming up with reasonable solutions in a short amount of running time. Let's spend a few minutes talking about hard problems. To start with, we need some vocabulary and some background on how to even talk about or characterize hard problems, so maybe it's worth our while to do a brief diversion into the world of computational theory and complexity theory. 

This takes us to some very deep mathematical questions about how do you characterize computation itself, how do you develop a mathematical model that describes computation. If you take a class in complexity theory or in the theory of computation, you'll study exactly this. You'll look at different models of computation and what problems they can and cannot solve and how efficiently they can and cannot solve certain types of problems. You have very simple types of models, and I won't go into the details here because I wouldn't want to deprive you of the fun of taking an actual class in the theory of computation. But for example, a finite state automaton, a machine that just transitions between a small set of states based on how it reads its input. That's a very simple model of computation, but it can only solve a very limited number of types of problems. You can then move from that to more sophisticated models of computation like a pushdown automaton. 

Now we have a finite state automaton that is like the CPU or the brain of the computer, but now the computer actually has a memory. In this case, in the form of a stack that's basically a stack of binary numbers. If you move from the pushdown automaton to a more sophisticated model, you could go to a Turing machine, which again it has a CPU in the form of a finite state automaton, but now it has an infinite two-way binary tape as its memory. There are different types of ways of modeling computational processes out there. We can actually prove that certain types of problems can and cannot be solved in these different models. Without giving you any definitions here, just to give you a sense of what we study in the theory of computation, there are certain types of problems called non-regular problems that are beyond the reach of finite state automata, but maybe those could be solved by more powerful models like pushdown automata. Then if you look at pushdown automata, they have limitations. 

They can't solve problems that are so-called non-context-free problems. For those, you might need a more powerful model like a Turing machine. One of the interesting things actually about the work of Turing and others was basically they hypothesized that the Turing machine is where this process ends, basically. Any problem that can be solved by algorithms, by systematic computation can be solved in principle by a Turing machine. There isn't a more powerful model of computation out there that can solve a broader class of problems than you can solve with a Turing machine. There are unfortunately problems out there that you cannot solve on a Turing machine, and those problems just simply cannot be solved by algorithms. These are called undecidable problems. 

There are a couple of prominent examples. Maybe the most famous is called the halting problem, which is given an algorithm and given its input, you have to predict if the algorithm will run forever on that input or if it will terminate. This is actually pretty easy to show to be an undecidable problem with a simple proof by contradiction. This is maybe bad news if you're writing an optimizing compiler that is going to look at a block of code and try and predict how you can optimize that block of code based on different types of input. The undecidable problems are just out of reach in terms of algorithms. The vast majority of problems out there, you can actually solve with algorithms. The question is, how efficiently can you solve them with algorithms? 

This takes us from the theory of computation into the realm of complexity theory, where we tend to take problems and put them into classes based on how efficiently they can be solved. There are hundreds and hundreds of complexity classes out there that people have studied. We'll briefly survey a couple of the most commonly known classes. But at a high level, we're basically trying to figure out for a new problem, can we solve it efficiently or not? As we've mentioned back in Module 1, the notion of efficiency typically means in the algorithmic community whether a problem can be solved in polynomial time in the size of its input. This has been the convention since the '60s when Edmonds originally introduced this notion that polynomial time should be equated with an efficient algorithm. At a very, very high level, your job as an algorithm designer is given a new problem, can you solve it efficiently or not? 

Can you solve it in polynomial time or not? How do we address that problem? Well, the first thing is we have to look at how problems are related in terms of their difficulty. This will help us build up a theory of what we can and cannot solve efficiently. A key idea here is the notion of a reduction. A reduction is something that lets us transfer the hardness result from one problem to another problem. If we go back to a problem we've talked about in the past, think about the element uniqueness problem. 

That is, given a set of n elements, are they all distinct or are there duplicates present in those n elements? It's known that in the comparison based model of computation, there's actually an n log n lower bound on the worst case running time of any algorithm that solves the element uniqueness problem. Now if you look at another problem maybe closely related, suppose we'd like to figure out in a set of n elements what's the most frequently occurring element. It turns out that the most frequently occurring element problem must also have a lower bound of n log n because of a reduction from element uniqueness to the most frequently occurring element problem. If you had a fast algorithm for finding the most frequently occurring element, you can see if that most frequently occurring element occurs with frequency two or higher, and that would give you effectively a backdoor solution to solving the element uniqueness problem. If, for example, you could solve the most frequently occurring element problem in only linear time, that would give you an indirect linear time solution for solving the element uniqueness problem. Since we know element uniqueness has a lower bound on it, that lower bound effectively transfers also to the most frequently occurring element problem. 

We can use these sorts of reductions to basically transfer a known hardness result from one problem to another problem. That's a very important idea in algorithms, is transferring hardness results this way. The same idea applies when you're talking about whether a problem can be solved efficiently or not. Let's here look at two more problems. The so-called Hamiltonian cycle problem is a famous problem in graph theory, where you're given a graph, a set of nodes and edges that connect those nodes, and you'd like to know, does that graph admit a so-called Hamiltonian cycle? That's a cycle that basically visits every node exactly once. This is a famous problem that we don't know how to solve efficiently. 

Another problem that's very similar in character is the so-called traveling salesman problem. This is given a set of n cities and the distances between those cities, you'd like to find a minimum length tour that visits every city exactly once. The tour would be a Hamiltonian cycle if you think of the cities as a graph. Here we can make a reduction that shows that that Hamiltonian cycle actually reduces to the traveling salesman problem. If you could solve the traveling salesman problem quickly, then you could compute whether or not a graph has a Hamiltonian cycle quickly. What you could do, for example, is you could take the graph that you'd like to find a Hamiltonian cycle in and you could add all the other edges into the graph and give them really high costs and give the original edges very low costs. Now if you could find a traveling salesman tour of low cost in this graph, you can only do that if the graph has a Hamiltonian cycle. 

These types of reductions will allow you to not only transfer hardness results in terms of running time lower bounds, but they also can tell you if one problem is efficiently solvable, whether another problem should be efficiently solvable or not. This is the basis for how we talk about complexity classes related to hard problems. Perhaps the most famous of these. I mentioned, there are hundreds of different complexity classes out there. Perhaps the most famous are the classes P and NP. P is basically a set of yes/no problems, decision problems that you can solve in polynomial time. Technically, that means on a Turing machine. 

But if you can solve it in polynomial time on a Turing machine, you can solve it in polynomial time on your cell phone or on your laptop. There are reductions that allow you to do that. P is basically the class of problems that we know how to solve efficiently. Given a new problem, we would like to know, does that problem belong to the class P or not? Can we solve it efficiently? Oftentimes that's hard to do because we just may not seem to be able to find an efficient solution to a problem. But in many cases, we can determine that the problem belongs to a much larger class or at least we suspect a much larger class called NP. 

The definition of NP is a little bit technical and I won't actually go into the fine-grained details. But NP, it doesn't stand for not polynomial. It stands for nondeterministic polynomial, and this contains all of the problems that you can solve in polynomial time with a non-deterministic algorithm. Non-determinism is an abstract concept. It doesn't really map to anything that you can achieve in reality. Maybe one way to think about it is that if your algorithm is executing, a lot of times it reaches a branch point where it has to consider one option and then another option as it's maybe searching over different possible solutions. A non-deterministic algorithm can actually explore all of those branches in parallel at the same time. 

It's similar to having an infinite level of parallelism available to your algorithm. If there's one execution path through your algorithm that confirms the answer to your problem is yes, then in polynomial time, then you can solve the problem in polynomial time with this non-deterministic algorithm. It's an abstract concept. It's a little bit weird, and there are other ways of thinking about non-deterministic algorithms. But basically, there's a huge number of problems that belong to this class NP that we don't know how to solve efficiently. For example, the Hamiltonian cycle problem is a problem that belongs to the class NP. Yes or no, does a graph have a Hamiltonian cycle? 

Now that we have those two classes vaguely defined, we can talk about the so-called NP hard problems. Those are the problems in NP that are the hardest of the problems in NP because there exist reductions that would allow you to show that if you could efficiently solve one of these NP hard problems, then every single problem in NP could be solved efficiently. That is something we strongly suspect not to be the case because there are thousands of problems in NP that we don't know efficient solutions to, very prominent problems that have been very, very well studied like the Hamiltonian cycle problem. If we could solve any one of these NP hard problems, that means that all the problems in NP could be solved efficiently. That's very strong evidence that these NP hard problems are, in fact, actually legitimately hard. Interestingly, no one has actually been able to prove this fact. No one has actually been able to prove that the problems in NP that are NP hard that you can't solve them efficiently. 

We just have this strong evidence that nobody yet has been able to devise an efficient solution to any of these NP hard problems. We very much suspect that NP is a bigger class of problems than P. If we could solve efficiently an NP hard problem, then the class NP would collapse down and that would be equal to P. This P versus NP problem is probably one of the most important theoretical questions of the day in computer science, resolving whether or not you can actually prove that the NP hard problems are actually difficult or not. There are different complexity classes that we can use to characterize hard problems. There aren't just NP hard problems out there. There are scarier complexity classes, #P hard problems, PSPACE hard problems. 

Complexity theory is a very vast discipline. It's an exciting discipline to look into, very mathematically deep if you're interested in further study in that area. This is the landscape in terms of how we can maybe characterize problems as being hard or efficiently solvable. Now, if your boss asks you to solve a problem and you seem unable to come up with an efficient solution to that problem, then the common adage here is that you can decline to solve the problem efficiently by telling your boss, sorry, I can show this as an NP hard problem. If I could solve it efficiently, that would be the biggest breakthrough in all of computer science. There are thousands of other problems out there that no one has been able to solve efficiently. All of those would now have efficient solutions if I could solve this one problem efficiently. 

This is touted as one of the benefits of the definition of NP hard because it gives you cover for not being able to solve a problem efficiently because you can point to it being NP hard, and therefore you solving it efficiently would imply big things in terms of the complexity of a wide range of other problems. Unfortunately, your boss would probably see things differently. Your boss would probably say, well, we still need to solve that problem. It's an important problem for whatever company we're running, and that is actually an important point of view. There are hard problems out there, and we still need to come up with effective ways of dealing with those hard problems. What should we do in the event that we're trying to solve a hard problem like the traveling salesman problem or a Hamiltonian cycle problem? This goes back to maybe a whimsical justification based on something you may have heard when you were a student at university. 

As the joke goes, if you're a college student, you get to only pick two out of these three desirable things. You could have good grades, you could have copious amounts of sleep, or you could have a strong social life. It's too much to ask for all three of these. You can only have two at the same time. I often hear the same choice being offered when it comes to hard problems. If you're faced with a hard problem, it seems like we can only achieve two out of these three desirable outcomes. We would like to be able to find an optimal solution to the problem, we would like to be able to solve every possible instance of the problem, and we would like to be able to solve them all efficiently with polynomial time algorithm. 

Unfortunately, we don't always get to achieve all three of these. We only get to pick two of the three. Depending on which two you pick, that basically defines what line of attack you're pursuing against that hard problem. If you forego option number 1, you're not going to find an optimal solution, but you'd like a solution for every instance that runs quickly. Now you're talking about maybe heuristics that give you reasonably good solutions, but in a fast running time. Later on in our enrichment lecture, we'll talk about approximation algorithms that give us provably close to optimal solutions with a fast running time. There are different lines of attack that forego optimality and still try and focus on getting reasonably good solutions. 

If you give up option number 2, now you're talking about the study of special cases. There could be a lot of problems for which finding a general solution is indeed a hard problem. But if you look at special cases of the problem that do appear in practice, then you can solve those efficiently. That's another viable line of attack. Then finally, you can forego option number 3, which means now we're just hoping to find an optimal solution, but we have to do some an exhaustive brute force search over maybe an exponential number of alternatives to find that solution. We'll also talk about in our coding discussion in this module how to do this exhaustive search as best we can using pruning techniques and whatnot to speed it up and get as much mileage as we can out of an exhaustive search. There are some different options available for how we can approach these types of hard problems.
