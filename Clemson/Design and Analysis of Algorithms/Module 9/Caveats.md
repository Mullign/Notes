![[Caveats.pdf]]Continuous optimization brings with it a number of key caveats that are worth keeping in the back of your mind as you develop algorithms in order to mitigate the probability of your algorithm behaving in some sort of an unintended way. So let's take a look at a couple of these issues. The first of them is floating point representation, and this of course is not only an issue that affects continuous optimization, but any algorithm in a domain where floating point numbers are common, say in computational geometry, for example. Because of the fact that floating point numbers essentially are stored as binary numbers written in scientific notation, there are certain numbers that are just not exactly representable in floating point. Say one third is not exactly representable in floating point. And so you'll have a slight amount of error there. You also get errors every time you operate on floating point numbers. 

You get small round off errors if you add, multiply, divide, what have you, to floating point numbers. And those can accumulate over the course of your algorithm. So you have to be very cautious in certain types of situations as a result of these anticipated round off errors. For example, if you want to test if two numbers are equal to each other, well, they're probably not going to end up being exactly equal because of these small errors. So instead, what you want to do is test if there are absolute differences within some sort of a small epsilon tolerance. If you want to, say, add a large number to a small number, that can be very risky because there's only a limited amount of precision in a floating point number. Most of that is being used up by the large number. 

And so there's not a lot of digits left that you're adding the small number into in terms of leftover precision. And so you can lose a lot of precision in the smaller number if you do this. To give an example of a situation where this could happen, I've used here a 32-bit float to basically keep a running sum as I add up 2 to the 20, that's about a million copies of 0.1. And so as that process unfolds, as my running sum gets bigger and bigger and bigger, I am now adding a very small number, 0.1, into my running sum, which is a much bigger number. So every single addition is an example of this bad phenomenon where you're adding a big number with a small number. And as a result, you actually end up with a total sum that is quite inaccurate compared to what it should be. A much better way to have done this would be using, say, divide and conquer, where you basically add up half of the numbers recursively and the other half of the numbers recursively. 

You get the same sum in both cases. And then you add those two sums together. And now that they're on the same order of magnitude, you don't have this issue where you're adding a big number to a small number. And you get a much more accurate result. Another situation that's maybe similar that you have to watch out for is sometimes called a catastrophic cancellation. Sounds very serious. If you subtract two numbers that agree in a large number of their initial digits, this can happen. 

So those initial digits all cancel out. And what you're left with is a very small number of remaining digits. And so you get a very low-precision answer if this sort of phenomenon happens. So basically, just be cautious any time you're dealing with floating point and be cognizant of these types of issues. Another situation that is quite common in a lot of numerical methods is poor conditioning. And this is a condition that exists on the input of an algorithm, not necessarily on the algorithm itself. So if you're trying to, say, solve a linear system, which in two dimensions means intersecting two lines, then normally that is perfectly fine, except maybe in the case where the two lines are almost parallel to each other. 

Because in that case, if you have a very small perturbation in any one of the two lines, then you can imagine that's going to have a dramatic impact on where the intersection point is. So a poorly conditioned input is one for which, if you have a very small change in that input, it could lead to an outsized, more dramatic change in the output. And so issues like round-off errors could be much more worrisome or dramatic in those particular cases. So you have to, with poorly conditioned inputs, maybe just warn the user or kind of test or watch out for them in your algorithms, because they can lead to outputs that are very unreliable or very error-prone because of the poor conditioning. The final situation that we want to definitely watch out for as well is instability in our algorithms. There are actually a lot of very well-known kind of household name algorithms that are known to be unstable, like Euler's method for integrating a differential equation. What instability means basically is that errors compound themselves over time, over the execution of the algorithm. 

So small errors in step one of the algorithm kind of feed back into step two and amplify a little bit. And then those feed back into step three, and the errors build up over time. And so that can be very dangerous if you don't kind of deal with the issue appropriately or kind of take appropriate steps to mitigate that. So on the right-hand side here, I've actually drawn a picture of Euler's method for recovering a function from its field of derivatives. So here the arrows basically give us a field of tangents that basically tell us the derivative of a function at every point in space. And starting from some initial point, we would like to basically just follow the arrows to trace out the function, to recover the function from its derivatives. And so the actual function is shown on top. 

That's the curved line here. Below it is the path taken by Euler's method. Euler's method is kind of the most simplistic method you can think of for recovering a function numerically this way. You basically just take a step in the direction of the first tangent, and then that lands you someplace. And then you take a step in the direction of the tangent at that location, and so on. If your step size is too big, then you can meander all over the place. And you can see how errors can compound, because once you're slightly off track, then you can get even more slightly off track, because the gradients might kind of diverge further and further away from the true function. 

So you can mitigate this, of course, by using a smaller step size, but then, of course, the algorithm is much slower. There are different approaches that are probably preferable to Euler's method, like Runge-Kutta methods for integrating differential equations, but it's good to keep in mind if you are planning to use some sort of simplistic method like Euler's method. Another class of methods that is known to be unstable are classes of methods based on Gram-Schmidt orthogonalization of vectors. This would be, hopefully, a common name that you've heard of if you've taken a linear algebra class, where you have a set of vectors, and you'd like to transform them into an orthogonal, a perpendicular set of vectors. Maybe I'll draw a picture of what that process looks like. So if I switch over to the whiteboard, if I have some initial vector, let's call this vector v1, and then I have another vector, let's call this v2, I would like to make v2 perpendicular to v1, and the way you can do that is you can look at the projection of v2 along v1 and subtract that out of v2, and that basically leaves you with the part of v2 that only points in the orthogonal or perpendicular direction from v1. And then if I have a vector v3, I can make it perpendicular to v1 and v2 by subtracting off the projection along v1 and v2, and I can continue doing that for a set of vectors. 

The trouble is, as you do that, for each subsequent vectors, errors tend to multiply because you have a slight error in the first subtraction, and then that error kind of influences the next vector that you try and make orthogonal, so you kind of lose orthogonality over time. And that can be a problem for not only the Gram-Schmidt algorithm, but for other algorithms based on essentially the same process. So there are algorithms for finding several eigenvectors of a matrix that are based on orthogonalization. There's the conjugate gradient method for solving a linear system, where you basically kind of optimize in one direction and then try and optimize in an orthogonal direction to that, and then optimize in an orthogonal direction to those original directions, and the same issue manifests itself with that algorithm. So just be cautious if you are using one of these algorithms known to be unstable. It's very important to be aware of the issue and, if possible, to take steps to mitigate it. So these are just a couple of issues that you can encounter in continuous optimization to be wary of, to make sure that you don't get unanticipated results as output.
