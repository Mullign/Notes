Let's briefly highlight some useful algorithmic connections between depth-first search and problems related to what we could call graph colorings. So there's a few problems in this space that are just good to know about. One of them is testing if a graph is a bipartite graph. Bipartite graphs are a very important subclass of graphs. Lots and lots of applications and problems involve bipartite graphs. Maybe the most prominent is a class of matching problems, where you'd like to match up the nodes on the left with the nodes on the right, and edges in your bipartite graph tell you pairs that are allowed to be included in the matching. So here the bold edges would be one way that I could match some of the nodes on the left with some of the nodes on the right. 

Maybe there's an even better matching that, you know, uses more edges. Typically you want to match up as many people as possible. So a bipartite graph, just to remind you of the definition, is a graph where you can partition the nodes into two sets. You typically draw them on, you know, one set on the left-hand side, one set on the right-hand side, such that all the edges go from one set to the other set. You don't have any left-left edges or right-right edges. You only have edges that go from the left to the right-hand side. Another kind of nice example of a bipartite graph is if you have a set of gears, then all of the adjacencies between the gears determine a graph, and that graph had better be bipartite, otherwise the gears won't turn. 

Because if you look at a gear, if that gear turns clockwise, all of the gears that are touching that gear, they have to turn the other way. They turn counterclockwise. And so you can't, if you look at the direction that all the gears are turning, that basically partitions the gears up into two sets, the clockwise gears and the counterclockwise gears. And all of the adjacencies have to be between different types of gears, you know, clockwise touching counterclockwise. And so the graph determined by your gears had better be bipartite if the gears are going to be able to spin at all, otherwise they would be locked in position. So the algorithmic question here of interest at the moment is, given a graph, can you test if it is indeed a bipartite graph? And that turns out to be actually quite easy using a full depth-first search. 

All you really need to do is kind of keep track of parity as you do your depth-first search. So keep track of whether you're on the left or on the right, or true versus false. So when you visit a node, maybe label that node as left, and then all of its neighbors have to be labeled with the opposite label, right. And then all of their neighbors have to be labeled left, and so on. So just keep track of that extra bit as you go. And if you ever discover an inconsistency, you're on a left node, and you have an edge to a node that you've already labeled as left, that means your graph was not bipartite. So basically just run a full depth-first search, and keep track of parity as you go, and monitor for inconsistencies. 

So in linear time, you can easily test if a graph is indeed bipartite. There's a related problem with an algorithm based on depth-first search that is almost the same thing. This is sometimes called the two-sat or two-satisfiability problem, and it involves finding variables that you can set to true or false to satisfy a Boolean expression that's written in a very particular way. The format of the expression has to basically be a set of clauses. Each clause has two variables, or the negations of their variables, and each clause itself is an or clause, like x or y, or not x, or z, and so on. And so you have a set of these clauses. The clauses only have two variables or negations thereof. 

That's why it's called the two-sat problem. And the clauses are all ANDed together. So if you want to satisfy this entire Boolean expression, you have to satisfy every single clause. So you have to satisfy the first clause. Either x or y has to be set to true to satisfy the first clause. And so here the goal is to figure out, can you satisfy the entire Boolean expression? Can you satisfy each one of these clauses? 

And it turns out that a very similar type of depth-first search mechanism can be used to solve this problem also in just linear time. And it's similar to what we did with the bipartite graph example. You're basically kind of tracking parity or kind of forced setting of values as you go. So for example, suppose we start out by guessing that x has to be false. If you guess that x has to be false, then there's kind of a graph underneath this expression. Every single clause involves two variables. So you can imagine there's kind of an edge that connects them that kind of implies a constraint between those two variables. 

So if x is set to false, y needs to be set to true. It has to be on the other side of the bipartite graph, so to speak. And so you can then fan out and kind of continue with your recursive search. Y being set to true might imply, since not y is in this clause, that means that z has to be set to true. And so you have to kind of continue basically propagating the ramifications of your variable settings, of your tentative variable settings, and looking for inconsistencies. You can come across an inconsistency with a variable you've already set, and that would mean that it's impossible to complete assignment of values to these variables. And so basically, you're just kind of running a depth-first search to test if the ramifications for starting with x being false lead to any inconsistencies. 

And if they don't, great. If they do, maybe try starting with x equals true and seeing if that does better. So basically, a very, very similar approach that you can use to solve the 2SAT problem. There are limits to how far this can be pushed, unfortunately. So the 3SAT problem, which is the same problem but with clauses involving three variables or negations thereof, that is one of the famous NP-hard problems that we don't know how to solve efficiently. And in general, kind of satisfiability problems tend to be among the hardest problems out there, algorithmically speaking. The one exception here is 2SAT, with only two variables per clause, because that kind of gives you an underlying graph structure that you can then exploit to solve in linear time with an algorithm that's basically depth-first search. 

So coming back to bipartite graphs, I wanted to also highlight their connection with graph colorability. So another way to describe a bipartite graph is to say that the graph is two-colorable. You can basically color its nodes in one of two colors that corresponds to the left and the right-hand side, such that every single edge goes from a node to a differently colored node. Another way to phrase that is to say that every color class, the set of all the nodes with the same color, that's an independent set. That's a set of nodes, no two of which are connected to each other. This is actually an important concept in, say, parallel processing. If you have a lot of tasks that you'd like to process in a parallel environment, a lot of times there are dependencies between tasks, so you can't run two of the tasks at the same time because they involve using the same resource. 

And so a lot of times you can build a graph where the tasks are the different nodes, and you connect together two nodes with an edge if they cannot be run simultaneously, that they have some sort of shared resource that they both rely on. And so what you can do is you can only run an independent set of tasks at the same time. And so if you would like to minimize the number of rounds required to run all of your tasks in parallel, then you would like to color your graph with a minimum number of colors, each color class corresponding to one round, one phase of your parallel algorithm. It's an independent set of tasks that you can all run simultaneously. So basically graph coloring is one key application, is parallel processing like this. Unfortunately, with a general graph, it is an NP-hard problem to find its so-called chromatic number. That is the minimum number of colors required to color its nodes into independent classes like this. 

But there are some interesting exceptions. And so two colorability is one interesting exception. We can test if a graph is two colorable, i.e. bipartite, in linear time using essentially a parity version of depth-first search. So two colorability is easy, but if a graph is not two colorable, then it becomes hard to determine the minimum number of colors required to color it successfully. One other famous result in the world of graph theory that you may have heard of is sometimes you may have heard of it called like the map coloring problem. It basically says that if you have a planar graph, that's a graph that you can draw in the 2D plane without any edges crossing, then planar graphs can always be four-colored. So in our earlier coloring example, we took the map of the United States. 

That actually does have a planar graph underneath it if you turn every state into a node and connect it with the adjacent states that share an edge, share a boundary with it. That gives you a planar graph. And so you could, if you tried hard enough, you could find a set of only four colors to color all the states of the USA such that adjacent states would be colored in different colors. I think if you meet at a corner, that doesn't count. They have to meet, you know, they have to actually share a non-zero extent boundary. So planar graphs can be four-colored, although it is still actually NP-hard to determine if less than four colors can be used. So if it's three colorable, for example. 

And it's also quite challenging algorithmically to calculate a four-coloring of a planar graph mathematically. There's a proof that it always exists. And I think you can do it in quadratic time, but I don't think the algorithm is particularly simple. So lots of interesting kind of lore, folklore, involving coloring out there that's kind of interesting to know about, but also some very practical problems and also highlights a nice additional set of applications of our standard depth-first search algorithm.
