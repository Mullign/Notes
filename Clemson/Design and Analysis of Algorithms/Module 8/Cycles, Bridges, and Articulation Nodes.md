In our continued attempt to convince you that depth-first search is indeed the Swiss army knife of graph algorithms, let's have a look at how we can extend depth-first search to identify cycles in graphs, as well as features called bridges and articulation nodes, which are very important features when you're talking about graph connectivity. Let's start with the case of cycles, and so we can consider asking in an undirected graph, is there a cycle? Or in a directed graph, is there a directed cycle? The directed case is maybe just a smidgen more complicated. The undirected case is extremely simple. So if your undirected graph, I guess first of all, if your undirected graph has no cycles in it, then we would call that graph a forest, because every single one of its components would be a tree. So how do we test if an undirected graph is indeed a forest, or if it has a cycle? 

That's very easy to do, because if any step of depth-first search tries to take you from your current node to a node that you have already seen before, that implies that you have found an undirected cycle in your graph, because you can go to that node you've already seen before and then continue following the path that took you to your present node. So basically every single step you take of depth-first search either takes you to a new node that you haven't seen before, that can happen at most n times, or takes you to a node that you have seen before, in which case you can stop then and there having discovered a cycle. So very easy in the undirected case. In the directed case, something kind of similar happens, but we have to be a little bit more careful, and in fact this requires that we basically classify nodes not only as having been unvisited or visited, but we introduce a third state which is called pending, and it turns out that we have a directed cycle in our graph if we ever try and follow an edge that would take us to a pending node. So let's look at what that means in the code of depth-first search. Here's how we'd want to modify our code. So normally with depth-first search, the first time you step on a node, you mark it as having been visited. 

In this case, we're going to mark the node as just pending the first time we step on it. So that's kind of in the process of being explored. We're in the process of exploring all the downstream nodes reachable from this particular node. And the code for visiting your neighbors doesn't really change, you only visit the neighbors that you haven't yet visited before. If you try and visit or discover a neighbor that is pending, that's the case where you have a directed cycle, and we'll draw a picture of that in a second. But only when you have completely finished visiting all of your neighbors, only then do you mark the node as kind of finally being visited. So we have these three states, unvisited, pending, and visited. 

The machinery that we've added here does not really change the running time complexity of depth-first search. And so a full depth-first search here still takes linear time, order of m plus n time, m being the number of edges, n being the number of nodes. This is what we call linear time, by the way, for a graph algorithm, order of m plus n, if the running time depends linearly on the number of edges and on the number of nodes. And as we remarked in the undirected case, we don't even have a dependence on m, the running time is just order of n, because every step takes you either to a new node, that happens at most n times, or it takes you to a node you have seen before, which you can stop right then and there having found a cycle. Let's draw a picture of what's going on here. If I switch my view to the whiteboard, suppose I run depth-first search on some node, that's going to start the node out as being in the pending state. And so at that point, I'm now exploring all the neighbors of this node. 

And so I explore a neighbor, that node gets set to pending, I explore a neighbor, that gets set to pending, and so on. This is kind of the structure of depth-first search, that's why it's called depth-first, because it dives into the graph as deeply as possible until you run out of options, until you reach a node where I have no neighbors yet left over to visit, they're all pending or visited, basically. So at that point, I stop and I back up. So if I have reached a node that I can't go any further, that node is no longer pending, but that node is now visited. And then I back up to the last node that I was at, and I continue my search. And so maybe now again, I have a pending node. And again, I have a pending node. 

Now remember that the condition for finding a directed cycle is if I try and follow an outgoing edge, and realize that that outgoing edge would take me to a node that is pending. And so you can actually see kind of what happens in that case. That pending node actually is an ancestor of you in the depth-first search. So if I kind of, if I follow that edge, that will take me to a node that is kind of one of the nodes that is kind of above me in the chain of nodes that are on the stack in the recursive process of being processed with depth-first search. So if I look at that series of nodes, that will lead me back to the current node that I'm processing, and that forms a directed cycle. So this is why we get a directed cycle from depth-first search anytime you try and follow an edge and realize it takes you to a pending node, because that's kind of a node that's an ancestor of your current node during the depth-first search process. And when we talk about actual path finding with depth-first search, it'll be easy to actually recover the cycle itself, not just say, yes, there is a cycle, but here's the nodes on the cycle, and the same thing in the undirected case as well. 

So depth-first search can be easily modified to detect whether a graph or a directed graph has a cycle still in just linear time. So let's talk about maybe one other application extension of depth-first search that's quite powerful in terms of analyzing the structure of the connectivity of a graph. So depth-first search can be modified such that in linear time, it can detect all bridges and articulation nodes in a graph. A bridge is basically kind of an edge that is a single point of failure in a graph. If that edge went away, then your graph would kind of fall apart into multiple connected components. An articulation node is the same thing, just it's not an edge, it's a node that is a weak point in your graph. So if I were to draw a picture of these things, say I have a connected component and I have an edge that connects to another connected component in the graph, that edge is a bridge. 

Because removing that edge would break what used to be one connected component up into multiple connected components. An articulation node is the same thing, but it's just a node that plays that same role. So if I have a single connected component that is kind of held together by that one node, such that deleting that one node would break the connected component into multiple pieces, that's an articulation node. So these are weak points in graphs. Very useful to be able to find these quickly because, for example, in a communication network, you probably don't want to have bridges or articulation nodes because if somebody accidentally breaks that wire, then you lose connectivity from one part of your graph to another part of your graph. So it's quite convenient that algorithmically we can find these things very quickly with depth-first search. Let's focus on the case of bridges.
