Suppose you'd like to solve the so-called all-pairs shortest path problem. That is, you'd like to find the shortest path from every node to every other node in a graph. Of course, you could approach this by running multiple invocations of a single-source shortest path algorithm. However, as we'll see in this video, there are actually some clever ideas worth mentioning that can be brought to bear in the context of the all-pairs problem. As our starting point, I'd like to talk a little bit about a remarkable algorithm called the Floyd-Warshall algorithm that solves the all-pairs shortest path problem in just order n cubed time. The algorithm is breathtakingly concise. That is really what makes it remarkable. 

If you look at the pseudocode here, it basically consists of just three nested for loops with an if statement in the middle. The running time being order n cubed is quite obvious from the structure of the pseudocode. The more difficult thing is to establish why this actually solves the all-pairs shortest path problem. We'll look at that now in a bit more detail. Let's look at the input first. The input to the problem is basically a matrix of edge costs describing our graph. Each entry in that matrix, Cij, tells you the cost of the edge from node i to node j. 

If there is no edge from i to j, that's effectively the same thing as there being an edge, but that edge having infinite cost. We're going to put infinities in our matrix any place where there isn't an edge. Finally, we're going to put zeros down the diagonal of the matrix to indicate that there's an implied zero-cost edge from every node back to itself. That's our input. It's a matrix of edge costs. After we run the Floyd-Warshall algorithm, that matrix will magically be transformed into a matrix of shortest path costs. Now the ij entry in that matrix will tell you the cost of a shortest path going from i to j, rather than just the cost of the direct edge from i to j. 

In fact, this is a very clean way to think about any shortest path algorithm. In the all-pairs case, it's basically a mapping, a transformation from a matrix of edge costs to a matrix of shortest path costs. One other nice feature about the Floyd-Warshall algorithm is that, like the Bellman-Ford algorithm, it can operate properly even in the presence of negative-cost edges. It can also detect the presence of those evil, pesky, negative-cost-directed cycles that prevent us from being able to calculate shortest paths properly. If you ever notice a diagonal entry in your matrix, one of these CII entries, turning negative, that effectively means the algorithm has discovered a negative-cost path from a node i back to itself, i.e. it's discovered a negative-cost cycle, and you can terminate then and there and basically throw up your hands and say, sorry, shortest path calculation just isn't going to work in this graph because it has a negative-cost cycle. So why does the Floyd-Warshall algorithm calculate shortest paths? It's probably easiest to think of the algorithm as a dynamic programming algorithm. 

It solves a series of increasingly more complex subproblems working towards the goal of calculating shortest paths. And those subproblems are actually relatively easy to define. So I've defined them here on the slide. So C superscript k, i, j, that's going to represent the cost of a shortest path from i to j that uses only some of the nodes in our graph as potential intermediary nodes. Only nodes 1 through k are allowed to be potential intermediaries along the path from i to j. So if you look at kind of what that is as a picture, then I'd like to find the shortest path from i to j, but it's only allowed to use 1 through k as intermediary. So the path is going to kind of hop from i into this cloud of potential intermediary nodes and then zigzag around in that cloud for a while and then finally hop to node j. 

That's what the subproblem C superscript k, i, j represents. That's the shortest possible path of this particular structure. And so now let's look at maybe the special case of what if k is 0? What if k is 0? There actually aren't any allowed intermediary nodes. What's the shortest path from i to j in that case? If you can't use any intermediary nodes, the only thing you can do is take the direct edge from i to j. 

And so C superscript 0, i, j, that's going to be just the direct cost of the edge from i to j. So C0 is our input matrix. That's the input matrix of all edge costs. What about C superscript n, i, j? Well, now we're allowed to use every node in our graph as a potential intermediary. And so there are no restrictions on intermediaries along our path. And so Cn, i, j is actually the cost of a shortest path from i to j. 

So C superscript n is the output of the desired output of the algorithm. That's the matrix of all possible shortest path costs. And so what we're basically doing is starting with the matrix C superscript 0. From that, we're calculating the matrix C superscript 1 and C superscript 2 and so on, working our way towards C superscript n. That's the final output. And you can see, based on the pseudocode, that that's kind of what's happening. Your outer loop is over k. 

And so when k equals 1, you're calculating the matrix C superscript 1, working your way towards, you know, when k equals n, when you're calculating C superscript n. And then the other two loops here are just filling in the entries in those respective matrices, the i, j entries in those matrices. All right. So let's now talk about the dynamic programming kind of recursive formula for calculating solutions of subproblems based on solutions of simpler subproblems that we've already calculated. So we want to figure out how to calculate Ck, i, j in terms of Ck minus 1 values. So we're going to be filling in the entries in the Ck matrix based on the entries that we've already calculated in the prior iteration in the Ck minus 1 matrix. So let's switch to the whiteboard to kind of see how that is done. 

So I would like to figure out how to calculate Ck, i, j using what I've already computed, which is the Ck minus 1 matrix values. And so suppose that, and in fact, I should probably redraw this figure just to make it avoid it being too messy here. So I have node i and node j, and I've already calculated, say, this matrix of Ck minus 1 values. So I know the optimal path to get from i to j using only nodes 1 through k minus 1 as intermediaries. And now I would like to use those values to help me compute the Ck values. The only difference now between the Ck values and the Ck minus 1 values is that now I have one more potential intermediary node that I could use. That is node k. 

So kind of node k is now included in this set of potential intermediaries. So how can I solve this subproblem? How do I get the optimal solution for allowing intermediaries through k? So one possibility is that I could just take, I might not even need to use node k, so I could just take Ck minus 1, i, j. That's the best path that uses nodes 1 through k minus 1 as intermediaries, and it doesn't necessarily use node k. So that would be one possible option. And so I'm going to take the better of that solution and the solution that does use node k as an intermediary. 

So what would that look like? Well, in that case, I would hop from node i into this cloud of potential intermediaries, you know, zigzag around for a while, and then land on node k. And then from node k, I'd go back into this cloud of intermediaries and then eventually end up at node j. And so that means I'm basically adding together two segments. One of them is the segment that goes from i to k, using intermediaries in the range 1 through k minus 1, and the other segment goes from k to j, using intermediaries in the range from 1 to k minus 1. So this is my dynamic programming recurrence, basically. I have two possible cases. 

I take the better of the two, and that tells me the best path from i to j, using potential intermediaries in the set 1 through k. Okay, so if I go back to my slides here, then what we can see is that the inner part of the algorithm here, this if statement, is basically implementing the DP recurrence. In fact, if I just substitute the DP recurrence here, then that's probably a good starting point for understanding how I can maybe simplify things a little bit. All right, so I basically have these three for loops that calculate the ckij values using my dynamic programming recurrence. So this is another way of thinking about the Floyd-Warshall algorithm. But the initial way that we wrote the algorithm didn't involve these subscripts. And in fact, you can simplify things by just kind of getting rid of the subscripts. 

You can actually just delete all the subscripts and deal with just one matrix. You don't have to keep track of separate matrices, like the c0 matrix, the c1 matrix, the c2 matrix. You can just keep track of just one matrix that is updated in place, and that actually ends up working with the Floyd-Warshall algorithm. So imagine that these subscripts aren't, these superscripts aren't even there. You're computing values in the ck matrix, but you're basically overriding that matrix. You started with the ck-1 matrix, and during iteration k, you're updating the matrix by filling in the ck values and just overwriting the values that were in the ck-1 version of the matrix. It turns out that that actually kind of works because by the time you're calculating the ckij value, you're taking the min of, well, ck-1ij. 

That entry hasn't been updated before. The only risk, I guess, is that these two values right here, the ck-1ik and the ck-1kj values, they might have been updated already to the ck values corresponding to those. However, those are actually the same numbers. If you look at ck-1ik, that's the same thing as ckik because k is an endpoint. It doesn't matter if you're allowed to use intermediaries through k-1 or intermediaries through k if k itself is an endpoint of your path. And so if these values had been previously updated at some prior point in our loop from the k-1 values to their k values, that wouldn't have actually changed those values at all. And so we can safely ignore superscripts and just keep one matrix in memory and overwrite the values in that matrix in each iteration, and everything actually just works. 

So that's one kind of simplification that makes the Floyd-Warshall algorithm especially simple. So if you go back to the way it's usually written, there are no superscripts, but you can still interpret the operation of the algorithm as solving this series of dynamic programming subproblems. So that's the Floyd-Warshall algorithm in a nutshell. It basically just has these three nested for loops and keeps updating entries in this matrix, and eventually that matrix is transformed into a matrix of shortest path costs. So a remarkably simple algorithm to implement. Okay, let's turn our attention to maybe now a second way of solving the all-pairs problem, and this goes back to our original observation that we could approach the all-pairs problem by running multiple invocations of a single source shortest path algorithm. And so if our graph has only non-negative edge costs, then that means we could run n invocations of Dijkstra's algorithm that will give us a running time of, I guess, if you run the version of Dijkstra's algorithm that uses a Fibonacci heap that achieves the kind of best known possible running time for Dijkstra's algorithm of m plus n log n, then you get an overall running time of mn plus n squared log n for the all-pairs problem. 

The challenge here occurs if your graph has negative edge costs, because in that case, things get very expensive because each of the single source invocations, they have to be the Bellman-Ford algorithm, which is much slower. So you have basically n times the running time of the Bellman-Ford algorithm, which is order mn. And so your overall running time for the all-pairs problem would, in this case, be m times n squared. That's really not great. That's going to be at least n cubed and possibly up to n to the fourth if your graph is very dense. And so this is the case we would like to kind of focus on and see if we can improve, basically the case where we have negative edge costs present in our graph, because we really don't want to run n times the Bellman-Ford algorithm. And so here's where we can bring in another really nice trick. 

What we can do, and this goes by the name of Johnson's algorithm, is that we can basically run one invocation of the Bellman-Ford algorithm and use the resulting cost labels that we've calculated to effectively reweight the edges in our graph in a way that effectively removes all the negativity. We will only have non-negative edge costs after this reweighting. And then after doing that, we can now just run n times Dijkstra's algorithm to finish calculating the solution of the all pairs problem. And so the overall running time that we're going to get is the same running time that we would get from n times Dijkstra because the running time of Bellman-Ford basically is dominated by that. The m times n from Bellman-Ford is part of that running time. So let's talk for a minute about how we can reweight our graph to remove negative cost edges. A lot of times when I mention to students that negative cost edges are a problem, they often suggest, well, why can't you just add a constant to all of your edge costs to get rid of all the negativity? 

Add a large constant to all of your edge costs. Unfortunately, that doesn't actually work. So if I switch to my whiteboard view here, suppose I'm looking at shortest paths, say, from node i to node j. And suppose I have a couple of different paths that I could use to get from node i to node j. So I have a path that maybe has only three edges in it, and then I have a path that has a whole lot of edges in it that goes from i to j. So if I add a common value to every single edge in my graph, like I increase every single edge by 17, then this top path is not affected that much because it only has three edges in it. So it only increases by three times 17. 

The bottom path increases by a lot because it has a lot of edges in that path. And so that actually gives you a disproportionate impact on the different paths between i and j based on how many edges were in those paths. And so what used to be the shortest path may not be the shortest path after this transformation. So you can't just kind of cheat and get rid of the negativity in your graph by adding a large common value to all of the edge costs. So that's a kind of a common misconception that I hear from students quite often. But there is, interestingly, a way that we can reweight the edges of our graph to remove negativity. We just have to be a little bit more clever about how we do it. 

So to do that, we have to actually introduce something called a reduced cost of an edge. So what I'm gonna do is solve one single source shortest path problem. Just pick an arbitrary source node and run the Bellman-Ford algorithm from that source node. What that's gonna do is it's going to compute a cost label for every single node in my graph. So C of i is gonna be the shortest cost of reaching node i from my source. A lot of times what we do here is we wanna make sure that we can actually reach all the nodes in our graph. If our graph is directed, sometimes it's the case that whatever source node you picked can't reach all the nodes in your graph. 

So sometimes we even just introduce a dummy source node with zero cost edges going to all of the nodes in our graph to guarantee that we can actually reach all of the nodes in our graph from our source node. And we use that source node for the initial shortest path calculation using the Bellman-Ford algorithm. So after we run that one invocation of the Bellman-Ford algorithm, we get a set of cost labels. And remember that if those cost labels do represent shortest paths, they will satisfy the triangle inequality. For every single edge in our graph, we have C of i plus the cost of the edge has to be at least as large as C of j. That's the same triangle inequality that we talked about back with Dijkstra's algorithm in edge tightening. Now, what if I rearrange the triangle inequality a little bit? 

What if I move the Cj to the other side? So I get this quantity, which is the original cost of the edge plus C of i minus C of j. I'm gonna call that the reduced cost of my edge, cost prime of ij. And you can see if you satisfy the triangle inequality, that reduced cost will actually be non-negative. And so this is a transformation of the edge costs in my graph that makes them all non-negative. The question is, is it a useful transformation? What's the benefit of changing the edge costs in this kind of weird looking way? 

So something actually rather nice happens if we transform our edge costs in this way. So let's again, look at this situation where I have a path, say from i to j, and suppose that path goes through a couple of intermediary nodes, like node one and node two and node three along the way to j. So now let's look at what is the cost of the path that goes from this particular path that goes from i to j. So the cost of the path originally is, I've got the cost from i to one plus the cost from one to two plus the cost from two to three and so on. I just add up the costs of the edges along the path. That's the cost of the path originally. Now, if I switch to using reduced edge costs, what is now going to be the cost of that path? 

And so what's the reduced cost of that first edge on the path? The reduced cost is going to be its original cost, the cost from i to one plus c of i minus c of one. That's what we called the reduced cost, cost prime of i to one. So that's the reduced cost of that first edge. What if I now add to that the reduced cost of the next edge? So I look at basically what is going to be the cost of my path now that I'm considering the cost of, after having been transformed into reduced edge costs. So the next edge is gonna have a cost, a reduced cost of a cost from one to two plus c of one minus c of two. 

And that's the reduced cost of the second edge in my path. And so on. You can kind of now see what's going to happen when I add all of these up. I'm gonna basically end up adding up still all of the terms that correspond to the original cost of the path. And something very interesting is gonna happen with these extra values, the plus and minus cost labels. So I have a minus c of one, and I have a plus c of one, and I have a minus c of two, and the next term is gonna have a plus c of two. So all of these are actually going to cancel out on me. 

This is called telescoping sometimes in mathematics when you have a large series and the terms of that series kind of cancel out consecutively with each other. What you're gonna end up with at the end of the day when you add all this up is mass cancellation. What is going to remain is the original cost of the path. And then you're gonna have a plus c of i that's gonna stay. And then at the very end, you're gonna have a minus c of j. Those are the only two extra terms. And so the reduced cost of my path is the same as the original cost with just an additive offset of plus c of i minus c of j. 

The nice thing is those two terms only depend on i and j. And so every single path going from i to j is offset by exactly the same amount, this plus c of i minus c of j. And so what used to be the shortest path from i to j is still going to be the shortest path from i to j, just its cost is going to be offset additively by this plus c of i minus c of j amount, which I know what that is because I know c of i and c of j. So if I calculate shortest paths with respect to reduced edge costs, I will get the same paths if I had calculated shortest paths using the original edge costs. So that's a very cool transformation. We managed to remove all the negativity from our graph while still preserving shortest paths. So now we can actually use Dijkstra's algorithm to calculate the shortest paths from every source node to every other node, and it will work properly because we have non-negative edge costs. 

So very, very cool. One other feature of reduced edge costs that I'd like to mention is that what is the reduced cost of an edge along a shortest path? So suppose I calculate shortest paths from some source node, and remember that that basically results in a tree of shortest paths. If you look at basically the tree defined by the predecessor pointers that you get from calculating shortest paths, you get an outgoing tree of all the shortest paths leaving the source node. What is the reduced cost of the edges on that shortest path tree? So it turns out that those edges actually satisfy the triangle inequality as an equality, and as a consequence of that, the reduced costs of all of these edges are gonna end up being zero. All of the other edges in the graph have non-negative reduced costs, but the reduced costs along those shortest paths from the source node that you used when calculating your reduced costs, those will actually end up having reduced cost of zero. 

So that's kind of a cool feature. In fact, there's a nice interpretation of reduced costs. Remember that when we talked about Dijkstra's algorithm, we talked about this kind of physical model of a graph with balls and strings where you can calculate shortest paths by suspending a graph by holding it by its source node, and all of the other nodes will drop according to gravity and kind of catch at a distance below the source node corresponding to the shortest path distance. You can think of the reduced cost of an edge as the amount of slack present in the string that that edge represents. So edges on shortest paths, they're stretched tight. They have no slack in them, so they have a zero reduced cost, but other edges may have a little bit of slackness in them, and that's the amount of reduced costs on those edges. It's always a non-negative quantity. 

We'll actually use that fact later on when we talk about matching problems. Reduced costs, we'll come back into the picture there, so it will be useful to have introduced them at this point. So right now, we're just using reduced costs as a convenient way of reweighting a graph with non-negative edge costs so that we can then subsequently use Dijkstra's algorithm to calculate shortest paths from all the other source nodes in our graph and therefore solve the all pairs problem much more quickly in basically n times Dijkstra running time. That's known as Johnson's algorithm. So these are just a couple of nice ways that we can address the all pairs shortest path problem in a graph. ♪♪
