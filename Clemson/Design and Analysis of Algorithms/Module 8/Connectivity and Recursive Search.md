The starting point for almost any discussion of graph algorithms is a very simple, very efficient and very flexible algorithm known as depth-first search. It's almost the Swiss army knife of graph algorithms because variations on depth-first search can be used to solve a tremendous number of fundamental graph problems, most of which have to do with connectivity. And we'll discuss these problems and how we can adapt depth-first search to solve them in the next couple of videos. Here's just a quick sampling of the types of problems that depth-first search can address. So are two nodes connected by a path in a graph? Are two nodes connected by a directed path in a directed graph? Partition up a graph into its connected components. 

Maybe partition a directed graph into its strongly connected components. Lots and lots of problems involving connectivity, pathfinding, and that sort of thing. And we'll see many more, in fact, over the next couple of videos. So in this video, we're going to focus on kind of global connectivity questions in graphs. So basically taking a graph and partitioning it up into its connected regions. And as a result of that, we'll be able to answer questions like whether nodes i and j are connected via some path. They will be if they live in the same connected region. 

And we'll also be able to answer similar questions about directed graphs. So depth-first search is an incredibly simple idea. It's much like some of the recursive searches that we've done in previous modules. For example, when we did recursive search in optimization. It's very straightforward. So what you do basically when you launch a depth-first search at some node in a graph is that you just mark that node as having been visited so that you don't get stuck visiting the same node over and over again, and then just recursively visit all of its neighbors in the graph. And that's it. 

That is depth-first search. So very, very simple idea. You make sure that when you visit a node, you only visit nodes you haven't visited before. So either when you enter a node, you check that, you know, have I visited this node before? And if you have, then bail out. Or when you're visiting your neighbors, you make sure you only visit the ones you haven't yet visited. So very, very simple idea. 

If you want to kind of look at it a little bit more at a pseudocode level, then we basically have two main functions. So we can have a DFS visit function. That's the function that is recursive and visits a particular node i. And so when we do that, the first thing we do is we mark node i as having been visited. So the status of node i kind of indicates, have I been there or not? And then all you do is look at all of the outgoing edges from node i. And for all of the downstream nodes connected to i that you haven't yet seen, you call DFS visit on those nodes. 

And that will just fan out and eventually visit all of the nodes that are reachable from node i in your graph. This works in a directed graph. This works in an undirected graph equally well. And the running time is quite easy to figure out. A lot of times we'll write the running time here as order of m plus n. And by convention, we typically take n to be the number of nodes in our graph and m as the number of edges in our graph. That's the convention that we'll use. 

A lot of other texts will use v plus e as the running time of depth first search. So v is the set of vertices in your graph and e is the set of edges. And so this would be written as, you know, order of the cardinality of the set of vertices plus the cardinality of the set of edges. The same thing. So you'll see this written in a few different ways. Sometimes you'll see the running time of depth first search written as just order m or just order of e under the assumption that the number of edges in most graphs is the dominant factor. Usually graphs have more edges than nodes. 

And so in that case, order of m would basically be the same thing as order of m plus n because m is the dominant factor. Why is this running time order of m plus n? Well, basically you spend a constant amount of work looking at every single node and a constant amount of work looking at every single edge in your graph. So order of m plus n in total. You can also consider a variation on depth first search. I sometimes call it a full depth first search that basically visits the entire graph. And so what that does is it loops over all the nodes in your graph. 

And as an initialization step, you set the status of every node to being unvisited. But then it makes another loop over all the nodes of your graph and any time it finds an unvisited node, it calls DFS visit on that node. So basically the first node you visit, you're going to launch a depth first search and that's going to fan out and visit everything reachable from that first node. Maybe that's not the entire graph though. Maybe your graph consists of several different connected components. And so your first call to DFS visit will discover one of those connected components, but it won't end up visiting everything in the entire graph. And so then it drops back down into this for loop and full DFS continues looping over all the nodes in your graph. 

And again, when it finds an unvisited node, it invokes another call to DFS visit, which will then kind of, you know, fan out and visit yet another connected component. And so this gives you a way of systematically visiting every single connected component in your graph with a recursive call to DFS visit. There are some benefits of doing that. So this basically partitions your graph up into its connected components. Oftentimes when you do this, you attach a label to every single node based on what component it's in. So maybe the first time you call DFS visit, you label all the nodes in the first component with ones. And then the next time you call DFS visit, you label all the nodes in the next component with twos and then with threes and so on. 

After doing that, it's now really easy to figure out if two nodes are reachable from each other, at least in an undirected graph. If they have the same label, then they live in the same connected component and you can reach one of them from the other via an undirected path. If your graph is directed and you'd like to know, is there a directed path from node I to node J, it's a little bit more complicated, but not by much. All you would do is you would launch a depth first search at node I, and that's going to go off and visit everything kind of downstream, you know, reachable via a directed path from node I. And if during that process you discover node J, then you know that there is indeed a path from I to J. And in a future video, we'll talk about how we actually recover the path from I to J. But right now we're just concerned with, you know, is I reachable from J or vice versa.
