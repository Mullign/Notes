There are lots of exciting things one can say about the algorithmic problem of finding shortest paths in a graph. This is one of the most prominent problems that we study from an algorithmic perspective when it comes to graphs. And this is also a problem that's fairly near and dear to my own heart because my master's thesis involved finding shortest paths in time-varying networks. That would be, for example, an automobile transportation network where you know that rush hour is on the horizon. And so you have to take that into account when you're finding a shortest path through the network because if you don't anticipate areas of the network that are going to slow down, you might end up routing yourself into what will become a very congested area of the network. So there are lots of different interesting variations on shortest path problems. In fact, let's probably make that the starting point of our discussion because part of the challenge with shortest paths is basically identifying the right algorithm for the right problem. So at a high level, we could talk about finding shortest paths from one node to another node, from a single source to a single destination. We could talk about finding shortest paths from one source node to all of the other nodes in a graph, the so-called single source or one-to-all shortest path problem. That's essentially equivalent, modulo reversing all the edges in your graph, to the single destination problem of finding the shortest path from every node to one common destination node. And then, of course, you could also ask for the shortest path from every node to every other node, the so-called all pairs problem. And of course, if you can solve the single source problem, you can run that on every single source node to solve the all pairs problem. If you can solve the single source single destination problem, you can run multiple invocations of that algorithm to solve a single source problem. But there are lots of algorithms that are kind of specialized for problems, one of these three problems basically, that might be simpler or easier to implement or analyze or more efficient. Usually when we talk about the shortest path problem, the standard problem that most people are focusing on is the single source shortest path problem. Given one source node, find the shortest path to every other node in a directed graph, possibly an undirected graph. If you have an undirected graph, you can, of course, replace every edge with a pair of bi-directed edges to turn it into a directed graph. So usually shortest path problems are considered in directed graphs. In terms of algorithmic results, it's kind of interesting that the single source single destination problem, for that problem, we currently don't know a better algorithmic running time, a better asymptotic running time, than for the more general single source problem. That's one of the reasons we maybe study the single source problem as one of our main problem variants. There are, of course, many heuristics available that can solve single source single destination problems much more quickly in practice than the more generic single source problem. We won't tend to focus on those in this class. We'll focus a little bit more on just the single source problem and a little bit on the all pairs problem as well. So what are the deliverables from an algorithm that solves the shortest path problem? So we'll focus from here on on the single source shortest path problem. So we have a graph that's directed. Every single edge has a cost associated with it, a weight or a length. We're going to use the word cost because that implies that you'd like to minimize the cost of the paths that you find. And so we have a designated source node. We'd like to find the shortest path from that source node to every other node. And so the output that you expect from your algorithm is typically two things. One is a so-called cost label for every node that tells you the cost of a shortest path to reach that node. 

And then you also would like to compute a predecessor pointer for every node that plays the same role as with depth-first search that we just talked about. That actually highlights the structure of all of the shortest paths leaving the source node. So collectively, all of these predecessor pointers will define a tree that is directed out of the source node. And that tree collectively describes all of the shortest paths from the source to every other node. The predecessor pointer of node j basically points to the penultimate node on a shortest path to node j. So if you want to reconstruct the shortest path to any node j, then you can follow the predecessor pointers in reverse to trace out that path as you work your way back towards the source node, just as we did with depth-first search. So these are the outputs that we expect of any single-source shortest path algorithm. Now there are several different types or flavors of algorithms for computing single-source shortest paths depending on the specifics of the graph that we're dealing with. We have already seen when we talked about dynamic programming that in a directed acyclic graph, in a DAG, you can actually compute shortest paths in linear time. 

You can solve the single-source shortest path problem in just linear time using dynamic programming, which is pretty cool. In this video, we'll talk about another special case where we can also solve the problem in linear time. That's order of m plus n time. That's using what's called breadth-first search, a very, very simple algorithm that's a relative of depth-first search. That only applies, however, if your graph is unweighted, if every single edge has a cost of one, in which case you basically want to find the minimum number of edges that it takes to reach every destination node, the minimum number of hops that it takes to reach every destination node. Moving beyond those special cases, it's very common to encounter graphs where all of the edge costs are non-negative, say in a transportation network that would tend to be the case. In that case, there's a very fast algorithm called Dijkstra's shortest path algorithm. Dijkstra was a famous computer scientist who passed away somewhat recently, but his name is associated with this algorithm. You can always remember how to spell it, by the way, because it has i, j, and k in alphabetical order. 

So this is a very common special case that we will study in a future video. So almost linear time for solving this special case, but that only applies if edge weights are non-negative. If you happen to have negative edge weights or edge costs in your graph, you need to use an algorithm called the Bellman-Ford algorithm or other types of algorithms that tend to be a little bit slower, but that they can handle these kind of more complicated negative edge costs. Now, one interesting thing about edge costs being negative is if it so happens that your graph has a negative cycle comprised of edge costs, so going around the cycle would have a net negative cost, then we're really out of luck because it turns out that in that case, it's actually computationally intractable to calculate shortest paths because a shortest path, we kind of prefer to go to such a cycle and go around it an infinite number of times to lower the cost of your path before proceeding on to the destination. So shortest paths aren't really even well defined in the presence of negative cycles in a graph. And even if you want to ask for, say, the shortest path that doesn't loop around on itself, that actually ends up being an NP hard question in the presence of negative cycles. So typically, when you have negative edge costs present in your graph, you have to at least assume that they don't contribute towards any negative cycles because that would make the problem intractable. Now, if you go back to, say, a directed acyclic graph, those graphs can have negative or positive edge costs. It doesn't matter because they're acyclic by definition, so they can't have these troublesome negative cycles. And so you can use dynamic programming in both cases to solve the problem in just linear time. Negative edge costs don't really matter in that special case, but they do matter a lot in the case of a general graph. 

All right, let's talk about, for the remainder of this video, the simple breadth-first search algorithm. It's a linear time algorithm that finds a minimum hop path from a source node to all other nodes in the graph. It assumes that every edge cost is essentially 1. So all we do, and it really lives up to its name quite nicely, is that you basically label the source node with 0 because it takes 0 hops to reach the source from itself. And then you label all the neighbors of the source with 1s because you can reach them with a single hop. And then you label their neighbors with 2s, and then their neighbors with 3s, and so on. So what you're basically doing is visiting the nodes of your graph in a kind of a layer-by-layer fashion. That's why it's called breadth-first search. So as you're visiting the nodes one layer out from the source, you're kind of labeling their neighbors with 2s because they are 2 hops away from the source. And then as you're moving on and visiting that layer of nodes, you are kind of labeling their neighbors, queuing up their neighbors as the next layer to visit, and labeling them with 3s, and so on. As a consequence of doing this kind of layer-by-layer traversal of your graph, you are going to identify shortest paths from the source to all other nodes. Every node will end up labeled with a cost label or a distance label that indicates the minimum number of hops it takes to reach that node. In code, this is relatively straightforward. It basically relies on the use of a queue to hold the working set of nodes that we intend to visit. So initially, we set the distance label of every single node to infinity except for the source node, which gets labeled with a 0. So distance of i is going to be the shortest path distance or cost of reaching every single node i. Every node is also going to have a predecessor pointer, as we've discussed before. And then all we're going to do is we're going to start with a queue of nodes we intend to visit. That queue is initially going to be just the source node. And then in the main loop of breadth-first search, we just visit the nodes in our queue one by one. And for every node that we intend to visit, we simply look at all of its neighbors. And for every neighbor you haven't yet visited, you're going to add it to the queue and give it a label that's one higher than your label. So when we visit the source node, we queue up all of its neighbors to be visited, and they get a label of one, one higher than what the source had. 

And then we proceed to visit those nodes. And for each of those nodes that we visit, we queue up their neighbors and give them distance labels of two, you know, one higher than the distance label that they have. And any time you add a new node to the queue, you have to set its predecessor pointer to the node that added it, basically a back pointer to your penultimate node on the shortest path that you've discovered. So relatively straightforward algorithm. It really is kind of visiting a graph layer by layer, starting from the source node, using a queue to kind of, you know, store the set of nodes that you're currently working with. There's really only two distance levels that are ever in play during a breadth-first search. Suppose you're currently visiting all the nodes at distance layer seven from the source. So there's kind of the current layer that you're visiting. And then there's the next level that you're queuing up at the end of your queue. So as you are visiting the nodes at distance seven from the source, you are queuing up the nodes to be visited at distance eight from the source. And then when you run out of nodes at distance seven, now you hit the part of your queue that involves the nodes at distance eight. And as you do that, you're starting to queue up nodes at distance nine and so on. Relatively straightforward algorithm. Interesting factoid, if you use a stack rather than a queue, just basically substitute out the dynamics of your underlying data structure, then you actually end up with depth-first search instead of breadth-first search, which kind of makes sense because of the recursive dynamics of depth-first search.
