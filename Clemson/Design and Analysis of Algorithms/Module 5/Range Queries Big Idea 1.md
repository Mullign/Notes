Our first big idea to talk about, we could maybe call it micro-macro decomposition. The idea here is I would like to take my input, here it's going to be a sequence, and I'm going to basically divide it up into big chunks. I'm going to pre-compute quantities on the chunks, and that's going to help me answer range queries much more effectively because I don't have to add up individual elements one by one to answer the range query; I can add up a bunch of whole chunks and save a lot of time by doing this. Here, the problem I want to solve is given a sequence, I want to support two operations, either modify an element in the sequence, given its index in the new value, or find the sum of any range. There are lots and lots of ways to address this particular question. I could have actually stored the sequence in the binary search tree and gotten a logarithmic running time for both of these operations. But that involves building a binary search tree and balancing it and all of that.

I don't have to actually add up individual elements, I can add up the contribution of those whole blocks in the middle. The total number of things that contribute to the range query is on the order of square root of n, square root of n whole blocks, and order of square root of n individual elements on the two sides. I get order of root n as my running time for all of these operations. This would work for just about any type of range query, sums, mins, maxes, what have you. You can definitely make things run much faster than this. But this is a very simple and very crude approach, and it actually generalizes quite well to a number of other situations where fancier data structures are harder to come by. This crude just micro-macro decomposition idea does show up a lot in a large number of situations in practice. 

Now, you can actually generalize that idea. If we go back, this is a two-level hierarchical decomposition of our sequence. We have the individual elements and then we have blocks on top of that. We could think about having blocks and then super blocks of blocks, have a three-level decomposition, and then maybe a four-level decomposition. If you actually take that idea to the extreme, what you end up with is a block with just two elements in it. Those are your two children. You end up with a logarithmic number of levels, you basically get a binary tree. 

That's the limiting process of that. Sometimes people call this a segment tree. It's a close relative of a binary search tree. I like to think of it as a fixed structure, complete, perfectly balanced tree that you build on top of a sequence. We have two ways, I guess, now of treefying a sequence. We could use a binary search tree, which encodes a sequence in its in-order traversal, or we could use this idea here, which builds a tree more on top of a sequence. The tree is going to be more of a leaf-oriented tree because the data is only stored in the leaves of our tree here.
