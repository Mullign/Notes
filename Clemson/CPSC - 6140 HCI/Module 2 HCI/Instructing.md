So let's look at the instruction interaction type. So this is where users can instruct a system, tell it what to do. And examples include, you know, the instructing, instructing the system to tell the time, provide a command to print a file, or to save a file, or to open a file. So it's a very common sort of conceptual model that users can apply to a computer system. And it's essentially underlying a diversity of devices and systems that range from processors, old school processors, to VCRs, to vending machines, to editing software, spreadsheets, for example, in which you're instructing the software system to perform some tasks. And it's the communication is essentially one way in which you instruct the system to do something, and then it performs the work in return. The main benefits is that instruction supports quick and efficient interaction. And it's good for repetitive kinds of actions performed on multiple objects. So instruction is quite common, and very, very popular, as systems are designed to carry out instructions that users provide inherently. In this slide, we are conducting an activity where we want to compare the instruction based interaction metaphor, a conceptual model, for two different types of interactions, possible interactions with a vending machine. The first vending machine on the left has been designed to use simple instruction. There are a small number of drinks to choose from, and each is represented by a very large button displaying the label of each drink. The user simply has to press one button, and this should have the effect of returning the selected drink. The second machine on the right is actually more complex, offering a wider range of snacks. And the trade off for providing more choices, however, is that the user can no longer instruct the machine by using a simple one press action. But now the user is required to use a more complex process involving first reading off the code. For example, C12 could correspond to a bar of KitKat, for instance, under the item chosen, then keying this into the number pad adjacent to the displayed item, and then checking the price of the selected option, ensuring the amount of money inserted is the same or greater, depending on whether or not the machine provides change. Problems that can arise from this type of interaction are the customers misreading the code, or miskeying in the code. That's happened to me many times, resulting in the machine not issuing the snack or providing the wrong item. A better way of designing an interface for a large number of choices of variable cost might be to continue to use direct mapping, but use buttons that show perhaps miniature versions of the snack placed in a very large matrix rather than showing actual versions. But this would, you know, use the available space in the front of the vending machine much more economically. The customer would need to only press the button of the object chosen and then put in the correct amount of money. There's less chance of error resulting from pressing the wrong code or the keys. The tradeoff for the vending company, however, is that the machine is less flexible in terms of which snacks it can sell. If a new product line comes out, they will also need to replace parts of the physical interface to that machine, which would be quite costly. So, you know, if you have many new products that you have squeezed in, you don't have enough buttons to show those new products. So, you may need to, again, design the physical interface back. So, those are some of the tradeoffs with regard to this conceptual model for these two types of vending machines.
